Critical — Fails WCAG 2.1 AA

Critical
Automated-mode hidden controls are invisible to keyboard but remain in the DOM with no inert
Console.jsx:666 · styles.scss:.cm-review-manual--hidden

When isAutomated === true the PR-number TextInput and both action buttons are hidden with display:none; visibility:hidden, which does correctly remove them from tab order. However, the approach is fragile: if any browser or assistive technology inspects the DOM before CSS is applied, or if focus is programmatically set by Carbon internals, a keyboard or screen-reader user can reach controls that appear to do nothing.

More importantly, display:none removes the element from layout but not from the accessibility tree in all AT/browser combinations. A future refactor that changes the hide mechanism (e.g. adding a transition) could silently re-expose it. The HTML5 inert attribute is the correct defence in depth here.

Recommended fix

Add inert={isAutomated || undefined} to the wrapping <div> in addition to the CSS class. This is a one-attribute change and requires no CSS modification. WCAG 1.3.1, 4.1.2.

Major — Significant barrier or WCAG failure

Major
Review-status indicator has no text alternative reachable via keyboard focus
Console.jsx:429–445

The Terminal-icon status indicator is wrapped in a div with role="status", tabIndex={0}, and a correct aria-label. However it is a plain div — not a button or a focusable widget — so it participates in tab order (good) but has no role that tells a screen reader it is interactive, and NVDA/JAWS will announce it as a generic container. The Carbon Tooltip wrapping it renders the tooltip on hover but may not reliably surface it on focus across all AT.

Recommended fix

Change role="status" to nothing (a status live region should not be focused) and move the accessible description to a visually-hidden <span> inside the element, or use Carbon's <Tag> to represent the status without adding it to focus order. If keeping it focusable for the tooltip, change the div to a button (disabled) or add role="img" with the aria-label. WCAG 4.1.2.

Major
ExpiryCountdown ticks every second but the live region is aria-live="off" — state change is invisible to AT
ExpiryCountdown.jsx:63–78

aria-live="off" is deliberate and correct for the ticking countdown (you don't want second-by-second announcements), but the transition from counting to "Expired" or "Renews on next call" is the meaningful state change that screen reader users need to know about. With aria-live="off" throughout, this transition is never announced.

Recommended fix

Keep aria-live="off" while counting. When expired becomes true, switch the span to aria-live="polite" (or add a brief role="status" element) so the transition to "Expired" or "Renews on next call" is announced once. WCAG 4.1.3.

Major
Bobcoins gauge chart has no text alternative — purely visual
BobcoinsPanel.jsx:322–333

The Carbon Charts GaugeChart renders an SVG arc showing budget percentage. Carbon Charts does not automatically provide an accessible text description of chart data. A screen reader user sees the balance figure and label in the sibling <p> elements, but gets no indication of the gauge's visual meaning (the proportion as a shape).

Additionally the gauge uses colour alone (blue/orange/red) to convey the urgency status. The prose sibling does not currently restate the status level in words. WCAG 1.4.1.

Recommended fix

Add aria-label={`Budget gauge: ${gaugeValue}% remaining (${gaugeStatus})`} to the .cm-coins__gauge div, and add aria-hidden="true" to the chart container so AT reads the label rather than the SVG internals. In the prose sibling, add the status word ("low", "warning", "ok") so colour is not the only signal. WCAG 1.1.1, 1.4.1.

Minor — Noticeable friction for AT users

Minor
The "dropped output" notice has no role and is never announced
ReviewLog.jsx:401–405

The <p> telling the operator "Earlier output was discarded" appears conditionally when the ring buffer overflows. It is important operational information. Without role="status" or aria-live, it is never announced to screen-reader users — they only see it if they happen to navigate to it.

Recommended fix

Add role="status" to the <p className="cm-log__notice"> that renders the dropped-output message (parallel to the clearError paragraph just above it, which already has role="status").

Minor
Missing component uses an em-dash as a decorative glyph without adequate context in the ledger table
BobcoinsPanel.jsx:130–136

The Missing component correctly hides the "—" from AT and substitutes "Not available". However, in the ledger table the substitution applies to cells for both "Spent" and "Remaining after". A screen reader user hearing "Not available, Not available" in sequence has no way to know which value is unavailable. The cell's column context (from <th>) helps, but only if the AT preserves table headers — which condensed structured lists do not always do.

Recommended fix

Change the visually-hidden text to include the column: "Spent: not available" / "Balance: not available", or ensure the StructuredList uses proper scope="col" headers so AT can associate the value to its column name.

Minor
PR progress list items don't describe the PR title to AT when only an icon indicator is shown
ReviewLog.jsx:363–392

Each <li> in the per-PR progress list contains: an IconIndicator (its label e.g. "Reviewed"), a PR number link or span, and an optional title. The IconIndicator announces its label, then the link announces "#123", then the title. This sequence is reasonable. However when there is no title, AT users hear "Reviewed #123" with no further context — fine if they know the PR, but a title would help, and it is only omitted when the agent hasn't parsed it from the log yet.

Recommended fix

No code change required — this is an inherent data-availability constraint. Consider adding an aria-label to the <li> element that combines status + number + title when all three are available: aria-label={`${meta.label}: PR #${pr.number}${pr.title ? ` — ${pr.title}` : ''}`}. This makes each row a self-contained, unambiguous announcement.

Minor
Help guide images — no surrounding figure/figcaption structure
HelpGuide.jsx:42–46, 92–96

Both annotated screenshots have descriptive alt text (good). However they are standalone <img> elements, not wrapped in <figure> with a <figcaption>. The relationship between the image and the accordion items that explain each lettered badge (A–F, G–I) is implicit only — a screen-reader user must infer it from proximity rather than a programmatic association.

Recommended fix

Wrap each image and its accordion in a <figure> with a <figcaption> that names the section. This is a semantic improvement with zero visual change. WCAG 1.3.1.

Minor
Schedule "Target" read-only field has no visible label element — uses a plain <p> instead
SchedulePanel.jsx:400–405

The "Target" field shows the max PR / days-back configuration using two plain <p> tags styled to resemble a form field. It is purely read-only data, which is fine. But it sits between form controls (the time input and the Save button), and its label ("Target") is a <p> with no programmatic association to the value. AT navigating the form by form elements will skip it; navigating by headings/text will reach it with no structural cue that it is related to the surrounding controls.

Recommended fix

Use a <dl><dt>Target</dt><dd>…</dd></dl> pattern (already used throughout the codebase for the same intent) or wrap in a Carbon FormGroup with a disabled read-only field so the label–value pair is programmatically associated. WCAG 1.3.1.

Enhancements — Exceed AA, improve user experience

Enhance
Add aria-describedby to the PR-number field linking to the inline error/warning
Console.jsx:668–691

Carbon's TextInput with invalidText does add an error message below the field, but the programmatic association between the field and the stale-input warnText relies on Carbon internals. Adding an explicit aria-describedby pointing to the helper-text element ensures AT reads the full context immediately on focus, not just on form submit.

Enhance
The completion modal's AI disclaimer should be associated with the modal heading
Console.jsx:887–901

The AI disclaimer at the foot of the review-complete modal ("AI-powered review can save time…") is important caveat text. It is visually separated by a border. Adding aria-describedby on the <Modal> pointing to the disclaimer paragraph would make AT read it automatically when the modal opens, without requiring the user to navigate to it.

Enhance
The "Confirm sign out" flow has no aria-live announcement for the transition
McpConnectionPanel.jsx:229–262

When "Sign out" is clicked, the button is replaced by "Confirm sign out" + "Keep connection" + a warning paragraph. The warning paragraph correctly uses role="status" (good), but the button swap itself is not announced. A keyboard user who tabs past the button and then returns will find different buttons without an audible cue that the set of available actions has changed.

Adding aria-live="polite" to the button container, or moving focus to the warning paragraph on the state change, would close this gap.

Enhance
Consider a lang attribute on <html>
client/index.html (inferred)

The app is English-only. Adding lang="en" to the root <html> element (in index.html) ensures AT uses the correct pronunciation rules and that translation tools detect the language correctly. This is a WCAG 3.1.1 success criterion at level A.

Enhance
Log body scroll container: add a visible label for AT explaining it is scrollable
ReviewLog.jsx:412–421

The log body has tabIndex={0} with aria-label="Review output" and a visible focus ring — well done. To additionally help AT users know the region is scrollable before entering it, consider adding a short aria-roledescription="scrollable region" or a visually-hidden hint like "Use arrow keys to scroll" via aria-describedby. This is a convenience improvement, not a failure.
