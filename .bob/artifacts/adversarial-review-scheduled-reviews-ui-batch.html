DimensionFindingRisk

4. Save changes / Unsaved changes / Discard changes

DimensionFindingRisk
Gap — dirty detection No existing "isDirty" concept in SchedulePanel.jsx. Must be derived correctly by comparing live form state (enabled, timeEST, timezone) against last-synced server values (lastSyncedSchedule). Timezone is tricky: it's lifted to Console and not part of the persisted schedule at all today — changing it currently has no save action and no server persistence call visible in api.setSchedule. Marking timezone changes as "unsaved" could be misleading if timezone is actually just a display preference, not a saved field. 45%
Regression — discard "Discard changes" must reset to lastSyncedSchedule-derived state exactly, reusing the same conversion logic already in the sync effect (~line 239). Risk of subtly different reset path (e.g. forgetting to reset timeDisplay/timePeriod together) causing a visible/logic mismatch (toggle reverts but time field doesn't, or vice versa). 30%
Regression — resetKey interaction The existing resetKey effect clears message on modal close but does not discard unsaved form edits. If a user edits, doesn't save, and closes the modal, current behavior silently loses the edit (item #4 exists specifically to warn about this) — but now the modal close and the "Discard" button both need to converge on the same reset behavior, or they'll drift into two different code paths for what should be one concept. 35%
Accessibility "Unsaved changes" in yellow text alone is a color-only signal risk (WCAG 1.4.1) — same category of finding already called out for confirm-buttons elsewhere in this codebase (McpConnectionPanel.jsx comment at line ~247). Needs an icon or explicit wording, not color alone, to stay consistent with the project's own established pattern. 30%
Copy consistency Button text change "Save schedule" → "Save changes" is generic — could read as ambiguous inside a modal that also has an MCP tab with its own separate save-like actions ("Save credentials"). Minor confusion risk if a screen reader user tabs between tabs. 10%

5. Clear stale PR input on automated → manual transition

DimensionFindingRisk
Gap — trigger condition Needs a useEffect keyed on the automated→manual transition specifically (not just "isAutomated is false"), otherwise prInput would be wiped on every render where automation is off, including the very first paint before a user has typed anything — harmless but wasteful, and risks wiping a value if isAutomated flickers null → true → false rapidly during initial load. 25%
Regression — data loss Directly contradicts the existing documented design intent at line ~637-641: "Manual controls — always in the DOM so the PR input field never loses its state." Clearing it on transition is a deliberate reversal of an explicit prior design decision for this exact field — worth flagging clearly since it changes documented behavior, not just adds to it. 40%
Edge case If a user has typed valid PR numbers, an admin enables the schedule elsewhere (another browser tab / another operator), and it polls in within 30s, the field is wiped without any warning or confirmation — silent data loss triggered by someone else's action, not the user's own. 35%

6. Shared pluralization/phrasing helper

DimensionFindingRisk
Gap pluralPRs is currently defined only in Console.jsx (unexported, module-private). Moving/exporting it from SchedulePanel.jsx (as previously suggested) creates an odd dependency direction — a page importing a helper from a component file it also renders. Cleaner: a small shared utils module, or keep it in Console.jsx and import into SchedulePanel.jsx instead (reverse direction), matching how toLocalTz/detectBrowserTimezone already flow from SchedulePanel.jsx → Console.jsx today (inconsistent either way without a decision). 25%
Regression Pure refactor of a pure function — near-zero behavioral risk if the import direction is resolved cleanly. 5%
